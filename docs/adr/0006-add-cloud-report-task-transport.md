# Add Cloud Report Task Transport

The local helper will add a cloud report task transport where it actively connects to a configured cloud server and receives report tasks over that outbound connection. This avoids relying on the cloud server reaching a user's local machine through NAT, firewalls, or dynamic network addresses.

Cloud WebSocket messages should be treated as task notifications, not large data transfer packets. Report templates and report data should normally be referenced by URL instead of embedded in the cloud WebSocket message.

Cloud printing requires explicit device management. Printer names are only unique inside a single Windows device, so the cloud server should not treat a printer name as a global identifier. A cloud printer should map to one cloud device and one local printer name.

Cloud device IDs must be globally unique and stable for one local helper installation. The helper should generate and persist a plain GUID device ID on first run when none is configured. The Windows computer name may be used as the default device display name, but not as the device identity.

Cloud devices are activated through a one-time activation code generated by the Admin system. On first use, the helper submits the activation code, device ID, device name, preview capability, default printer, and current printer list to `/admin/platform/cloudPrint/devices/activate`. After successful activation, it persists the returned long-lived device token and uses that token for future WebSocket connections. Activation codes are not stored as long-term credentials.

Cloud WebSocket messages use a common envelope shape: `type`, `requestId`, `timestamp`, and `data`. The envelope keeps connection, task, result, error, and printer-report messages consistent for logging and troubleshooting.

Cloud WebSocket connections use the cloud-print device channel. The local helper connects to `/platform/gridReport/cloud/ws` with the device token in the URL query string as `token={deviceToken}` and repeats the token in the initial `hello` envelope. The helper should not add custom HTTP headers during the WebSocket handshake, so it stays compatible with strict gateways that reject extra `Connection` header values such as `keep-alive`. Open-platform API signatures apply to third-party HTTP APIs, not to the local helper's device WebSocket channel.

The local helper currently uses a manual reconnect model. When connection fails or closes, the user can trigger reconnect from the main window. After every successful connection, the helper sends a hello message and reports the current printer list again. The local helper does not persist or queue cloud tasks while disconnected; the cloud server remains the source of truth for pending tasks.

Cloud device online state is determined by the cloud server. The local helper sends heartbeat messages every 30 seconds while connected. The cloud server marks a device online when the WebSocket connection is established and marks it offline when the connection closes or no heartbeat is received for 90 seconds.

The local helper reports printers after connect, after reconnect, when the user manually refreshes printers, and on a lightweight five-minute interval. The cloud server upserts printers by cloud device and local printer name. Printers missing from a later report should be marked unavailable instead of deleted so historical cloud task audit records remain readable.

**Consequences**

Cloud transport is the active report task transport. It should not require exposing a local listening port to the internet.

Cloud task messages should stay small enough for stable proxy and client handling. A practical target is under 64KB per message, with a conservative hard ceiling around 256KB unless the cloud server and client are explicitly configured otherwise.

Cloud transport will not send edited report template content through `save-report`. Template maintenance for cloud workflows is handled by uploading template files through the Admin system, keeping cloud WebSocket traffic focused on task delivery and task results.

The cloud server needs a minimal device model for routing and audit. Cloud-print related system tables should use a `system_` prefix:

- `system_cloud_device` stores the helper installation identity, display name, connection status, and last heartbeat time.
- `system_cloud_printer` stores the printer list reported by each cloud device.
- `system_cloud_task` stores cloud-delivered report task audit records, including the target cloud device and, for print tasks, the selected cloud printer or device-local printer name.

This keeps cloud printing auditable without turning report tasks into a complex workflow engine.

`system_cloud_task` should remain a simple audit table. Its minimal fields are `id`, `request_id`, `device_id`, `printer_id`, `cmd`, `template_url`, `data_url`, `ext_info_json`, `status`, `result_message`, `result_json`, `error_message`, `created_at`, `sent_at`, and `completed_at`. Task status should stay limited to `pending`, `sent`, `success`, and `failed`.

A successful print task result means the local helper submitted the print action locally. It does not prove that paper was physically printed. Cloud task result messages report local helper execution outcomes through the common envelope with `taskId`, `cmd`, `success`, `message`, optional `result`, and optional `errorCode` in `data`.

Cloud transport supports only `print` and controlled `preview` task commands. `preview` is intended for attended devices and should be controlled by device configuration such as `allow_preview`. Cloud transport does not support `get-printers`, `design`, or `save-report`; printer discovery is handled by printer-report messages, and template maintenance is handled by the Admin system.
